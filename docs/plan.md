# 專案計畫:Tenant SaaS(Rust 多租戶系統)

## 目標
用 Rust 做一個多租戶 SaaS 後端,學習 axum / sqlx / Postgres RLS,並產出可展示的作品。

## 領域:預約排程
- 租戶 = 一間店家(診所、美容院、教室、顧問等)
- 員工(擁有者 / 管理者 / 員工)管理服務項目、營業時間、預約
- 顧客不需註冊,在店家公開頁選服務與時段後預約,以 Email 確認
- 一個員工帳號可屬於多間店

### MVP 範圍
| 層級 | 功能 |
|---|---|
| 帳號 | 員工註冊、登入、加入多間店 |
| 店家(租戶) | 建立、邀請員工、三種角色、時區設定 |
| 服務 | 服務項目(名稱、時長、價格)、員工可提供的服務 |
| 營業時間 | 每週營業時段、休假日 |
| 預約 | 查詢可預約時段、建立 / 取消 / 改期、防止重複預約 |
| 顧客端 | 公開預約頁(依店家子網域)、Email 確認 |
| 通知 | 預約確認信、前一天提醒信(背景任務) |
| 方案限制 | 免費版限制員工數與每月預約數 |

### 先不做
付款、候補名單、多分店、行動 App、Google 日曆同步

## 技術選型
| 項目 | 選擇 |
|---|---|
| Web 框架 | axum |
| 資料庫 | PostgreSQL + sqlx |
| 租戶隔離 | 共用表 + `tenant_id` + RLS |
| 認證 | JWT 或 session、密碼用 argon2 |
| 授權 | RBAC(租戶內角色 + 平台超管) |
| 背景任務 | apalis 或 Redis + tokio |
| 快取 / 限流 | Redis、tower-governor |
| 計費 | Stripe(async-stripe) |
| 日誌 | tracing |

## 架構重點
1. 租戶識別:子網域或 JWT claim,以 middleware / extractor 取得已驗證的 `tenant_id`
2. 資料隔離:每個 transaction 內 `SET LOCAL app.tenant_id`,搭配 RLS policy
3. 權限:租戶內角色(管理員、操作員、唯讀)+ 平台層超級管理員
4. 租戶限額:員工數、每月預約數、API 速率,對應訂閱方案
5. 稽核日誌:記錄誰在何時改了什麼
6. 租戶生命週期:註冊、停用、資料匯出、刪除

## 里程碑
| 階段 | 內容 | 預估 |
|---|---|---|
| M1 | 專案骨架、migration、健康檢查 | 1–2 天 |
| M2 | 註冊 / 登入 / 密碼雜湊 | 3–5 天 |
| M3 | 租戶與成員關係、租戶中介層、RLS、**隔離測試** | 1 週 |
| M4 | 服務項目、員工、營業時間 CRUD | 1 週 |
| M4.5 | 預約核心:可預約時段計算、防重複預約(排除約束)、時區 | 1–2 週 |
| M5 | RBAC 權限 | 3–5 天 |
| M6 | 背景任務(寄信、報表) | 1 週 |
| M7 | 訂閱計費與限額 | 1–2 週 |
| M8 | 稽核日誌、可觀測性 | 3–5 天 |
| M9 | Docker 化與部署 | 2–3 天 |

## 風險與注意事項
- 時間一律以 `timestamptz` 儲存(UTC),顯示依租戶時區轉換;營業時間以「租戶本地時間」儲存
- 重複預約由資料庫排除約束(`btree_gist`)把關,不只靠應用層檢查
- 公開預約端點要限流、防機器人,避免被灌爆時段
- 背景任務 / cron 必須帶租戶上下文,避免跨租戶操作
- 快取 key 一律加 `tenant_id`
- 檔案上傳路徑按租戶分目錄
- `SET LOCAL` 必須在 transaction 內使用,否則設定會殘留在連線池
- 隔離測試是最重要的測試:證明 A 租戶看不到 B 租戶資料
