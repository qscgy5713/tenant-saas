# 設計決策紀錄

格式:日期、決策、原因、替代方案。

## 2026-10-02 租戶隔離方式:共用表 + tenant_id + RLS
- **原因**:成本低、Rust 生態支援順、RLS 在資料庫層強制過濾,即使應用層漏寫條件也不會外洩
- **替代方案**:每租戶一個 schema(migration 複雜)、每租戶一個資料庫(營運成本高)
- **狀態**:暫定,M3 實作後驗證

## 2026-10-02 Web 框架:axum
- **原因**:tokio 生態主流,與 tower middleware 整合佳
- **替代方案**:actix-web

## 2026-10-02 資料庫存取:sqlx
- **原因**:編譯期檢查 SQL,不需 ORM 的額外抽象
- **替代方案**:sea-orm、diesel

## 2026-10-02 領域:預約排程(取代原暫定的充電場域管理)
- **原因**:使用者希望做大部分人都用得到的產品;預約排程顧客端人人可用,又有時段衝突、時區等真實技術挑戰
- **替代方案**:團隊任務管理(多租戶練習較完整但使用者偏上班族)、表單收集(太簡單)
- **取捨**:顧客不需帳號,成員關係較單純,以「員工可屬於多間店」補足
