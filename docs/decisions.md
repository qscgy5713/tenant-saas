# 設計決策紀錄

格式:日期、決策、原因、替代方案。

## 2026-10-02 租戶隔離方式:共用表 + tenant_id + RLS
- **原因**:成本低、Rust 生態支援順、RLS 在資料庫層強制過濾,即使應用層漏寫條件也不會外洩
- **替代方案**:每租戶一個 schema(migration 複雜)、每租戶一個資料庫(營運成本高)
- **狀態**:暫定,M3 實作後驗證

## 2026-10-02 Web 框架:axum
- **原因**:tokio 生態主流,與 tower middleware 整合佳
- **替代方案**:actix-web

## 2026-10-02 資料庫存取:sqlx
- **原因**:編譯期檢查 SQL,不需 ORM 的額外抽象
- **替代方案**:sea-orm、diesel

## 2026-10-02 領域:預約排程(取代原暫定的充電場域管理)
- **原因**:使用者希望做大部分人都用得到的產品;預約排程顧客端人人可用,又有時段衝突、時區等真實技術挑戰
- **替代方案**:團隊任務管理(多租戶練習較完整但使用者偏上班族)、表單收集(太簡單)
- **取捨**:顧客不需帳號,成員關係較單純,以「員工可屬於多間店」補足

## 2026-10-02 RLS 套用方式:交易內 SET LOCAL ROLE tenant_app
- **原因**:單一連線池即可;擁有者 / 超級使用者預設繞過 RLS,切換成 `NOBYPASSRLS` 角色後才真正受約束;交易結束角色與上下文自動還原,不會殘留到下一個請求(有測試)
- **替代方案**:另開以 `tenant_app` 登入的第二個連線池(需管理兩組連線與密碼)
- **風險**:有人繞過 `begin_scoped` 直接對 `PgPool` 查租戶表,在超級使用者連線下會繞過 RLS。規則:租戶資料一律經 `begin_scoped`;正式環境連線使用者不可是超級使用者

## 2026-10-02 租戶不放進 JWT
- **原因**:使用者可屬於多間店,切換店家不必重新登入;每個請求用 `/t/{slug}/...` 即時驗證成員資格,停權或移除成員立即生效
- **取捨**:每個租戶請求多一次查詢(成員資格)

## 2026-10-02 非成員與店家不存在一律回 404
- **原因**:不洩漏某個網址代稱是否已被註冊 / 存在(有測試比對兩者回應完全相同)

## 2026-10-02 防重複預約:應用層驗證 + 資料庫排除約束
- **原因**:應用層「先查再寫」在併發下一定有空窗(有破壞性測試證明:拿掉約束後 8 個併發請求有 2 個同時成功)。約束是最後防線,應用層只負責擋明顯無效的請求並給友善錯誤
- **做法**:`EXCLUDE USING gist (tenant_id, staff_user_id, tstzrange(starts_at, ends_at)) WHERE status IN (confirmed, completed, no_show)`;違規(23P01)回 409,不指定員工時用 savepoint 退回再試下一位

## 2026-10-02 營業時間以本地時間儲存,計算時依時區換算
- **原因**:「每週一 09:00 開門」是本地概念,不隨夏令時間改變。若存 UTC,夏令時間切換後整套時間會偏一小時
- **夏令時間**:跳時造成的不存在時刻整段略過;回撥造成的重複時刻取較早者(皆有單元測試)

## 2026-10-02 公開預約防濫用
- 每來源限流(記憶體內固定視窗,預設 60 次 / 分鐘);單一 Email 最多 5 筆未來預約;最遠 90 天;既有顧客的姓名電話不被後續預約覆寫
- X-Forwarded-For 預設不信任,開啟後只取最右一筆(最右是自家代理附加的,左邊可被偽造)
- **已知缺口**:Email 未驗證。限流與上限只能提高成本,擋不住有心人用大量不同 Email 佔位,M6 寄確認信後改成確認才占位
- 多實例部署時限流各自計算,需要全域限流時改用 Redis

## 2026-10-02 顧客預約「確認後才占位」
- **原因**:先占位再驗證,攻擊者可用任意 Email 在限流下持續佔住時段;確認後才占位,沒有信箱控制權就占不到任何位置。壞處是兩人申請同一時段時,先按確認的贏,後者會在確認時收到衝突訊息(有測試)
- **做法**:`pending` 不在排除約束的條件內;確認那一刻轉 `confirmed`,衝突(23P01)就把這筆標為 cancelled。確認時還會重新驗證時段(申請後可能新增休假)
- **token 不回傳**:建立預約的回應不含管理 token,只在信裡;否則呼叫者可替別人的 Email 確認
- **確認用 POST**:信中連結導向前端頁面,頁面按下按鈕才送 POST。若用 GET,信件安全掃描器自動點開連結就會替對方確認
- **已知限制**:可對他人 Email 觸發驗證信(每店每 Email 最多 5 筆待確認 + IP 限流,24 小時後才釋出名額)

## 2026-10-02 寄信:資料庫 outbox + 內建 worker,不引入 Redis / 外部佇列
- **原因**:信與業務資料同一個交易寫入,不會「預約成功但信沒排進去」或相反;`FOR UPDATE SKIP LOCKED` 讓多個 worker 實例不會重複寄;少一個要維運的元件
- **取捨**:吞吐量上限比專用佇列低,對預約系統的信量遠遠足夠;日後量大再換
- **隱私**:信裡有一次性連結,寄出(或最終失敗)後立即清空 body,資料庫不長期保留 token;排程時間一律用資料庫時鐘

## 2026-10-02 背景 worker 的權限:獨立角色 `tenant_worker`
- **原因**:worker 要跨租戶處理,但不該是超級使用者。它沒有 BYPASSRLS,只對需要的表有明確政策與權限(測試證明:讀不到 `password_hash`、不能刪預約、不能寫服務、讀不到 memberships)

## 2026-10-02 店家後台:同一個前端專案、獨立 chunk、權限只決定顯示
- 放在 `web/src/admin/`,以 `React.lazy` 載入:顧客預約頁不下載後台(約 17KB gzip)。共用設計 token、`SlotPicker`、時間工具
- ~~JWT 存 localStorage~~(2026-10-05 起改為 HttpOnly cookie,見下方「HttpOnly cookie 登入」)。嚴格 CSP 與 `csp.test.ts`(防行內 script / eval / `dangerouslySetInnerHTML`)仍保留,是 XSS 的第一道防線
- **登出 / 過期 / 401 一律清空所有快取**:同一台電腦的下一位使用者不能看到上一位的資料。有兩條路徑(登出鈕、登入狀態消失時的 hook),各自有測試
- **登入後只回站內的 `/admin`、`/invitations`**,防開放式重新導向
- **前端的權限判斷只決定「顯示什麼」**:員工看不到稽核 / 方案入口,直接輸入網址會看到「沒有權限」且不會打那兩支 API。真正的檢查一律在後端(員工打 API 仍是 403)
- **邀請連結 token 放在 `#` 之後**:fragment 不會送到伺服器,不進存取紀錄與 Referer。後端邀請信同步改成 `#token=`
- **嚴格 CSP 的後果是行內 `style` 不能用**(用量條寬度、頭像顏色都改用 class)。因為開發環境沒有這個限制、會「開發正常上線壞掉」,所以用 `csp.test.ts` 在測試階段擋下
- 營業時間 / 休假的時間輸入一律以**店家時區**解讀,不是操作者瀏覽器的時區(店主出差時也不會設錯)

## 2026-10-02 顧客預約頁只做淺色主題
- 原本跟隨系統的深色模式,使用者的電腦是深色,整個預約頁變成黑底,被要求改掉。對象是一般顧客,預約頁預設就該明亮、友善;`color-scheme: light` 也讓表單控制項不被系統強制變暗
- 設計參考 Fresha、Square(白底卡片、大圓角、留白、單一強調色):沒有照片,所以用漸層標題區 + 店名縮寫頭像,並加上步驟指示
- **可互動元件的邊框要夠深**:輸入框、時段、人員選擇的邊框原本與白底只有 1.64:1,WCAG 1.4.11 要求 ≥ 3:1;卡片、分隔線仍用柔和的邊框。停用的主按鈕改成淺灰底 + 深字(原本白字配灰綠只有 3.6:1,而那顆按鈕上的字是顧客要讀的提示)

## 2026-10-02 前端:React + TypeScript + Vite,放在同一個儲存庫的 `web/`
- 使用者選定。React Query 管資料請求(快取、重試策略);React Router;沒有 UI 套件,自己寫 CSS(約 500 行,以 token 管理顏色)——頁面少、設計要貼近參考產品,不值得為此引入元件庫
- **API 走同源 `/api/` 代理**(開發用 Vite、正式用 nginx,去掉前綴),所以後端不需要 CORS;之後若要前後端分網域再加
- **時間一律以店家時區顯示**,日期用 `YYYY-MM-DD` 字串表示「店家當地的日曆日」。顧客約的是實體世界的時間,不是自己瀏覽器時區的時間
- **確認預約必須按按鈕(POST)**,不在載入管理頁時自動送出:信件安全掃描器會先點開信中的連結
- **有副作用的請求絕不自動重試**(預約、確認、取消、改期);查詢遇到 4xx 也不重試
- **5xx 不顯示後端內容**:只給固定訊息與 `X-Request-Id`,避免洩漏內部細節
- 管理頁網址含 token:nginx 加 `Referrer-Policy: no-referrer`、`noindex`、`no-store`、嚴格 CSP、`frame-ancestors 'none'`
- 先做顧客端:它是產品核心、後端公開 API 已齊全、也最適合對外展示;店家後台下一階段

## 2026-10-02 資料庫帳號:migrator / runtime 分離,runtime 碰不到租戶資料表
- **原因**:超級使用者、BYPASSRLS、資料表擁有者都繞過 RLS。runtime 帳號 `NOINHERIT`,本身只有 `users`(註冊 / 登入)與 `plans` 的權限,租戶資料一律得先 `SET LOCAL ROLE tenant_app`。漏掉 `begin_scoped` 的程式碼會 permission denied(失敗即關閉),而不是悄悄越權
- **啟動檢查**:`APP_ENV=production` 時帳號過大就拒絕啟動,而不是只在文件裡叮嚀
- **migration 與 runtime 分帳號**:runtime 沒有建表 / 建角色權限,SQL injection 的破壞範圍小很多;`migrate` 是一次性命令,不在應用程式啟動時執行
- **取捨**:多一個角色要佈建,且需要 PostgreSQL 16+;`users` 仍需直接存取(登入時還沒有租戶),`password_hash` 因此對 runtime 帳號可讀——這是已知的剩餘暴露面

## 2026-10-02 bookings 不再 FORCE RLS
- 原本 `bookings` 是 FORCE RLS,但 `booking_tenant_by_token()` 是 SECURITY DEFINER,以擁有者身分在沒有租戶上下文時讀它。FORCE 下擁有者也受政策約束 → 讀不到 → 預約連結悄悄 404。之前只因 migrator 碰巧是 `tenant_worker` 成員(該角色有 `USING (true)` 政策)才運作
- 改為只 `ENABLE`,與其他會被 SECURITY DEFINER 函式碰到的表一致。**不削弱隔離**:runtime 與 `tenant_app` 都不是擁有者,仍完全受 RLS 約束
- 教訓:超級使用者環境下的測試通過,證明不了受限帳號下也通過。所以新增 `restricted_role` 測試與 CI 工作,並刻意撤銷 migrator 的成員資格

## 2026-10-02 正式環境不允許 Log 模式寄信
- Log 模式把信件內容(含一次性連結)印進日誌,等同把取消 / 改期 / 加入店家的權限寫進日誌。只給開發用;`APP_ENV=production` 沒設 `SMTP_URL` 就拒絕啟動(要暫時不寄信請設 `WORKER_ENABLED=false`)

## 2026-10-02 登入與註冊限流
- 每來源每分鐘 10 次(`AUTH_RATE_LIMIT_PER_MIN`),比公開預約端點嚴格。超過後連正確密碼也被擋——這是限流的目的
- **限制**:IP 層級、單一實例記憶體內。分散式暴力破解、跨實例需要帳號層級鎖定與 Redis,尚未做

## 2026-10-02 稽核日誌:同交易寫入、只增不減、不記個資
- **同交易**:變更成功才有紀錄、失敗一起消失(有測試:被擋下的第 6 個服務、重複邀請都不留紀錄)。`create_tenant()`、`accept_invitation()` 執行時沒有租戶上下文,所以稽核寫在 SQL 函式裡
- **只增不減**:`tenant_app` 只有 SELECT / INSERT,`tenant_worker` 只有 INSERT(連讀都不行)。這是資料庫層的保證,不是靠應用程式自律(有測試,也做過突變驗證)
- **不記個資**:因為刪不掉,寫進去的 Email、電話、備註、休假原因就收不回來。只記識別碼、狀態轉換、欄位名稱。代價:要查「是哪位顧客」得回頭用 booking id 查,這是刻意的
- `actor_user_id` 不設外鍵:使用者離開後紀錄仍須保留;顯示時 LEFT JOIN 取目前姓名
- 不記錄:登入 / 註冊、授權失敗、讀取。這些量大且性質不同,日後用安全日誌處理

## 2026-10-02 日誌與指標只用路由樣板
- **原因**:預約管理 token 在網址路徑裡,預設的 `TraceLayer` 與 `DefaultMakeSpan` 會把完整 URI 寫進日誌——取得日誌的人就能取消 / 改期任何顧客的預約。改記 `/public/bookings/{token}`。同樣,指標的 `path` label 對不存在的路徑用固定的 `unmatched`,避免攻擊者製造無限多個 label
- 請求 ID 只接受英數、`-`、`_` 且 ≤ 64 字,否則換掉:它會進日誌,不能讓用戶端偽造日誌行
- `/metrics` 預設不存在(404);設定 `METRICS_TOKEN`(≥ 16 字元,不足則拒絕啟動)才開放,並以固定時間比對 token

## 2026-10-02 限額的併發控制:per-tenant advisory lock,不用 SERIALIZABLE 或計數欄位
- **原因**:「先 count 再 insert」在讀已提交下一定會超賣。`pg_advisory_xact_lock(hash('quota:{種類}:{租戶}'))` 讓同一家店同一種資源的檢查+寫入序列化,不同店、不同資源互不阻塞,交易結束自動釋放
- **替代方案**:SERIALIZABLE(需處理重試,影響整個交易);獨立計數欄位(要和真實資料保持一致,刪除 / 取消時容易漏);
- **風險**:Rust 的 `plan::lock` 與 SQL 的 `accept_invitation()` 各寫一份鎖 key,改了一邊另一邊就失效。已有測試持有同一把鎖來驗證兩邊都會等待
- **取捨**:鎖範圍是整家店的某種資源,寫入量很大的店家會在該資源上排隊;預約系統的量級可接受

## 2026-10-02 限額語意
- 成員數 = 成員 + 未過期未接受的邀請(邀請會預留名額);撤銷或過期釋出
- 服務數 = 啟用中的服務(停用不算;重新啟用要重新檢查)
- 每月預約 = 該店當地月份內 confirmed / completed / no_show;取消不算,待確認不算。確認、員工代客預約、跨月改期都計入
- 降級後超出新上限的既有資料不強制清理,只擋新增
- 對顧客一律說「額滿」,不暴露方案名稱與上限;員工與 owner 才看到 402 與方案資訊

## 2026-10-02 方案只能由營運端改
- `tenant_app` 對 `plans`、`tenants.plan_id` 無寫入權限(測試證明),避免店家自行升級。升降級由 Stripe webhook(見下)或營運人員處理

## 2026-10-02 計費:方案只由 webhook 改變,計費資料不給租戶角色
- 結帳完成導回的網址參數不可信,方案只在驗證過簽章的 `customer.subscription.*` 事件後才變;前端導回後輪詢(最多 15 次)等 webhook 生效
- `tenant_billing`、`stripe_events` 租戶角色與執行階段帳號都無直接權限,只能透過 SECURITY DEFINER 函式:`billing_state` / `billing_attach_customer`(租戶上下文)、`billing_apply_event`(webhook,只授權給 runtime;租戶上下文內呼叫會被拒絕——有測試)
- 事件去重(`stripe_events`)與亂序保護(只套用 `created` 不早於已套用的事件)寫在資料庫函式內同一交易;付費中卻對不到方案(price 沒設定)回 500 讓 Stripe 重送,且該事件不會被記成已處理
- `past_due` 維持付費方案(寬限期,由 Stripe 的重試與最終取消事件決定);`incomplete` 不改方案;`canceled/unpaid` 退回免費版。降級不刪資料,只擋新增
- 客戶建立使用 idempotency key(`tenant-customer-{id}`),同時兩個結帳請求不會建出兩個客戶;已有進行中的訂閱回 409,要變更走客戶入口
- 只有店主能操作付款(manager 也不行)

## 2026-10-02 忘記密碼
- 不洩漏帳號是否存在:不論 Email 是否註冊都回同樣的 202,且應用程式端兩種情況做的事相同(都先產生 token 與信件內容,由資料庫函式決定要不要寫入)
- 同帳號每小時最多 3 次申請(函式內計數),避免被拿來灌爆別人的信箱;token 只存 SHA-256、1 小時、單次;用掉一個就作廢該帳號所有未用的重設連結
- JWT 無法撤銷,所以 `users.password_changed_at`:驗證登入時若 token 簽發時間早於改密碼時間就拒絕(順便讓「使用者已被刪除」的 token 也失效)。代價:每個已驗證請求多一次主鍵查詢;簽發時間只到秒,同一秒內的舊 token 有約 1 秒窗口
- `email_outbox.tenant_id` 改為可空(重設信不屬於任何店家);租戶角色因 RLS 看不到這些列,只有 worker 看得到

## 2026-10-02 改期的提醒與去重鍵
- 舊 bug:改期後 `reminder_queued_at` 沒清、提醒去重鍵是 `reminder:{id}` → 永遠不會再提醒新時間。改為 `bookings.reminder_seq`(每次改期 +1),鍵為 `reminder:{id}:{seq}`;不用開始時間當鍵,因為 A→B→A 會撞鍵

## 2026-10-02 重寄確認信
- 顧客沒收到信就沒有 token,所以用「預約編號(建立時回傳)+ Email」確認身分;重寄會換新 token,舊信裡的連結隨即失效
- 限制記在預約上(`verification_resends` ≤ 3、`verification_sent_at` 間隔 ≥ 60 秒),只有「待確認且未滿 24 小時」才能重寄
- 不論有沒有真的寄出都回同樣的 202(編號不存在、Email 不符、已確認、已過期、超過次數都一樣),不洩漏預約是否存在。取捨:合法使用者連按時看到成功訊息但實際沒寄,前端按鈕在重寄後停用 60 秒來避免
- 已知風險:知道編號與 Email 的人可以讓他人最近一封確認信的連結失效(最多 3 次),但拿不到新 token

## 2026-10-06 取消原因
- **只寫進信,不存**:原因常含個資(「他生病了」「家裡有事」),而稽核日誌只能新增、不能刪;預約備註欄是給店家內部看的,混進去會被匯出。所以原因只存在於寄出的那封信,稽核只記 `has_reason`。信寄出後 outbox 的內容也會被清掉。代價:事後查不到當時寫了什麼
- **只有真的會寄信時才問**:只有「已確認、還沒開始」的取消才會通知顧客(待確認的 Email 沒驗證、過去的預約通知只會造成困惑),所以介面只在那種預約顯示欄位,送出時也只在那時帶上;後端對其他情況也接受(不報錯),但不會寄出。**關閉對話框會清掉**,否則 A 顧客的原因會被帶到 B 顧客
- **郵件標頭注入**:原因絕不進標題(標題裡的換行會變成多的標頭);控制字元(換行與 Tab 除外)一律拒絕 —— NUL 會讓資料庫寫入失敗(500),CR 可用於偽造標頭
- 多行原因的每一行縮排兩格,看得出是店家說的,不是系統信件本身的內容
- 原因只能和 `status: cancelled` 一起送(單獨送是 400),避免它被誤以為是備註
- **已知風險**:店家人員可以在官方寄出的信裡放任意文字(含網址)。帳號被盜用時可被拿來釣魚。緩解:200 字、純文字、不可改標題與寄件人。沒有完全排除

## 2026-10-06 服務的整理時間(緩衝)
- **語意**:服務結束後員工還要整理 N 分鐘。顧客看到的預約時間不變(`starts_at` / `ends_at`),員工的行程占到 `blocked_until = ends_at + N`。只有「員工何時能接下一筆」受影響
- **`bookings.blocked_until` 是預約當下的快照**,不是每次用服務的 `buffer_minutes` 即時算:店家改了整理時間,不能讓**已存在**的預約突然互相衝突(例如原本 10:00–10:30 與 10:30 開始的兩筆緊貼著,把整理時間從 0 改成 15 就變成互相重疊,卻已經是既成事實)。改設定只影響新的預約。代價:多一個欄位與一個 trigger
- **資料庫是最後一道防線**:排除約束改用 `tstzrange(starts_at, blocked_until)`。應用程式的可預約時段計算只是「建議」,並行請求要靠資料庫擋(測試直接對資料庫寫入驗證,繞過應用程式也擠不進整理時間)
- 計算規則(`compute_slots`):新預約占住 [開始, 結束 + 自己的整理時間);和既有預約(含它們的整理時間)比對。**休假只比對服務本身**:整理時間伸進休假不算衝突(員工在休假前收拾完)。**服務必須在營業時間內結束,但整理時間可以超出打烊**(員工收拾完才下班)。這兩個是產品決定,不是技術限制
- 安全網 trigger:沒指定 `blocked_until` 的寫入預設等於 `ends_at`(沒有整理時間);只改 `ends_at` 的更新保留整理時間的長度。應用程式一律明確寫入,trigger 是給手動修資料與舊測試用的
- 範圍 0–120 分鐘(資料庫 CHECK + API 驗證);整理時間不出現在任何公開 API(測試確認)
- `compute_slots` 的參數收成 `Timing { duration, buffer, step }`(原本 8 個參數,clippy 抱怨,而且 `duration` / `buffer` / `step` 都是 `Duration` 很容易傳反)

## 2026-10-06 匯出預約與刪除顧客個資
- **不做「刪除預約」,做「匿名化顧客」**。硬刪除預約會破壞稽核的對象關聯、營業統計與員工行程,而「這筆不要了」取消就夠了。真正有法律 / 信任意義的是顧客要求刪除**他的個資**。所以把「這位顧客是誰」抹掉,預約留著
- 匿名化 = 姓名 `已刪除的顧客`、Email `deleted-{顧客id}@anonymized.invalid`(`.invalid` 是保留的頂級網域,保證不是真地址;**帶 id 才能各自唯一**,否則第二位被刪的顧客會撞 `(租戶, Email)` 唯一限制 —— 測試涵蓋)、電話清空;預約備註清空(備註常寫著個資)
- **信件佇列也要處理**:沒寄出的信直接刪(顧客要求刪除後不能再寄信給他);已寄出的紀錄改成匿名地址。`email_outbox` 只授權一般請求 SELECT / INSERT,所以用最小功能的 SECURITY DEFINER 函式 `outbox_forget_recipient`(限目前租戶、限指定收件者、需租戶上下文)
- **只有擁有者能刪**:不可逆。有「未來的已確認」或「待確認」預約時拒絕(那位顧客還等著被服務、還會收到信),要先取消。**過去但還沒標完成的「已確認」預約不算**(測試涵蓋)
- 重複刪除回 409,不重複處理、不重複記稽核
- 稽核只記「誰刪了哪位(id)、影響幾筆預約、移除幾封信」,不記任何個資(測試掃過整個資料庫確認找不到原本的姓名 / Email / 電話)
- 預約匯出:管理者以上(員工不能一次帶走全店的顧客資料)。與稽核匯出共用 CSV 工具(公式注入防護 / 引號 / BOM)與 50,000 筆上限(改放 `csv::EXPORT_MAX_ROWS`)。篩選語意與列表相同(與期間「重疊」的預約)
- **這兩個功能都要在受限帳號下測**(碰到 RLS 與資料庫函式):已加進 `restricted_role` 測試,並驗證過收回函式權限時它會以 500 失敗

## 2026-10-06 稽核日誌匯出與查看顧客個資的紀錄
- **CSV 公式注入是這個功能最重要的風險**:匯出檔有使用者自己填的文字(操作者姓名)。任何人註冊時都能把姓名設成 `=HYPERLINK(…)`,管理者匯出後用 Excel 一開檔就會執行。對策:欄位開頭是 `=` `+` `-` `@`(或 Tab / 換行)就加單引號。測試用 RFC 4180 解析器把檔案**還原**後比對(而不是比字串長相),確認引號、逗號、換行來回無損
- UTF-8 **BOM**:Excel 開沒有 BOM 的 UTF-8 會把中文當亂碼。CRLF 換行(RFC 4180)
- 兩個時間欄:UTC(給程式)與店家當地時間(給看報表的人)
- **匯出本身要留紀錄**(`audit.exported`:誰、條件、幾筆),而且與讀取在同一個交易:超過上限而失敗的匯出沒有帶走資料,就不留「匯出過」的假紀錄。紀錄是讀完之後才寫,所以不會出現在自己的檔案裡
- **超過 50,000 筆回 400,不截斷**:被截斷的稽核資料比沒有更糟 —— 看起來完整,實際缺了。測試精準驗證邊界(剛好 50,000 可以、多一筆拒絕)
- 後台用 `fetch` 下載再存檔,而不是 `<a href>`:失敗時(例如超過上限)才能在畫面上顯示原因,而不是下載到一個內容是錯誤訊息的檔案
- 查看顧客個資:`customer.listed` / `customer.viewed`。**搜尋字串不寫進稽核**(稽核只能新增、不能刪,寫進去的個資收不回來);只記筆數與是否有搜尋。沒權限(403)、找不到(404)、參數錯誤(400)都沒看到資料,所以不留紀錄
- 不做的:預約列表 / 預約詳情的瀏覽稽核 —— 那是店員每天的例行操作,每次都記會把真正重要的紀錄淹掉

- 休假清單:原本 `LIMIT 500` 硬上限,超過的看不到也刪不掉。改成預設只列「還沒結束」的(這是管理者會需要看的),已結束的另外看。**分頁用 `has_more`(多抓一筆)而不是 total**:不需要另一次 count,而且剛好整頁、後面沒有時 `has_more` 正確是 false(測試涵蓋)
- 順手修了一個定時炸彈:舊的休假測試用寫死的日期 `2026-12-24`,過了那天就會變成「已結束」而壞掉。改用相對於現在的日期

## 2026-10-06 每位收件者的寄信量上限
- 威脅:公開預約頁任何人都能填任意 Email,系統就會寄驗證信過去。單一店家已有「同一 Email 最多 5 筆未來預約」,但攻擊者可以對很多家店各來一次 → 受害者信箱被灌爆,而且信是「我們的系統」寄的(寄件網域信譽受損)
- 範圍:只限制**寄給外部指定收件者**的路徑(公開預約驗證信與重寄、代客預約確認信、邀請信)。這些收件者不是系統能信任的人。不限制:重設密碼(已有每帳號每小時 3 封)、鎖定通知(每次鎖定一封)、顧客 / 店家取消與改期通知(收件者已有預約關係,而且觸發者是登入的店家人員)
- 計算方式:資料庫函式 `mail_quota_ok()`(SECURITY DEFINER),因為 `email_outbox` 有 RLS,一般請求看不到別家店的信,算不出跨店家的數量。**依賴 0022**(outbox 不 FORCE,擁有者才看得到全部)
- **加鎖**:以收件者為單位的 `pg_advisory_xact_lock`,持有到交易結束;呼叫端在同一個交易內接著寫入信件,所以並行請求不能同時通過檢查(測試:同時 8 個請求、上限 2,恰好 2 個成功)
- 回應:公開預約回 429(通用訊息,不透露是哪個收件者被限制的細節);**重寄驗證信靜默拒絕**,回應與其他靜默拒絕(預約不存在、太頻繁…)完全相同,不洩漏預約是否存在
- 已知取捨:這個限制本身可被利用 —— 攻擊者可以替別人的 Email 預約把額度用掉,讓對方在一小時內無法用自己的 Email 預約(預設 6 封)。比起讓人被灌爆信箱,這是較小的傷害,而且一小時後自動恢復
- 邀請接受端點改掛與登入 / 註冊相同的限流

## 2026-10-06 修正:email_outbox 的 FORCE RLS 讓三個功能在正式環境壞掉
- **發現**:要加新的寄信限制時,注意到 `email_outbox` 是 `FORCE ROW LEVEL SECURITY`。而「忘記密碼」(`request_password_reset`)、「帳號鎖定通知」(`login_failed`)、「付款失敗通知」(`billing_payment_failed`)這三個 SECURITY DEFINER 函式都在**沒有租戶上下文**時寫入它。FORCE 讓擁有者也受政策約束,政策是 `tenant_id = app_tenant_id()` → NULL → 寫入被擋
- **實際後果(在正式環境的受限帳號下重現過)**:忘記密碼整個 500;帳號鎖定第 5 次失敗拋錯 → 交易回滾 → 次數永遠停在 4 → **根本鎖不住**,攻擊者只是拿到 500;付款失敗 webhook 500 → Stripe 一直重送。忘記密碼自 `ce90ddb` 起就是壞的
- **為什麼沒被抓到**:所有一般測試與 e2e 用超級使用者連線,**超級使用者繞過 RLS**。CI 的 `restricted-role` 工作是為了抓這類問題而存在,但它沒涵蓋這三條流程
- **修法**:migration 0022,`email_outbox` 改 `NO FORCE`(與 0011 對 `bookings` 同一個做法)。不削弱隔離:擁有者是 `tenant_migrator`,只用來跑 migration 與執行這些函式;`tenant_app` / `tenant_worker` 都不是擁有者,仍完全受 RLS 約束
- **防再發**:`tests/restricted_role.rs` 補上這三條流程(忘記密碼 → 收信 → 重設;5 次失敗 → 401 且鎖得住 → 收通知信;付款失敗 → 店主收信)。已驗證:拿掉修正時這個測試以 500 失敗,套用後通過
- **通則(寫給之後的自己)**:任何 SECURITY DEFINER 函式,只要碰 FORCE RLS 的表(目前:`customers`、`email_outbox`、`services`、`staff_services`、`time_off`、`working_hours`),**必須**在受限帳號下測過;超級使用者的測試證明不了。新增這類函式時,把它加進 `restricted_role` 測試
- 重現方法:另開一個全新的 PostgreSQL 叢集(角色是叢集共用的),照 CI 的 `restricted-role` 步驟佈建,再用 `RESTRICTED_RUNTIME_URL=… cargo test --test restricted_role -- --ignored`

## 2026-10-05 提醒信的改期 / 取消連結
- 問題:資料庫只存管理 token 的雜湊,提醒信(確認後一兩天才寄)拿不到原始 token
- 排除的做法:① 存可還原的 token(資料庫外洩就等於所有預約外洩);② 提醒時換掉原本的 token(確認信裡的連結會悄悄失效,顧客收藏的連結壞掉);③ 用伺服器密鑰推導 token(密鑰輪替會讓所有信中連結失效,而且和「重寄確認信換新 token」的設計衝突)
- 採用:**第二個專用 token**。提醒信寄出時由 worker 產生,只存雜湊;公開端點的查詢改成 `manage_token_hash = $1 OR reminder_token_hash = $1`。確認信的連結不受影響;兩封信的連結是不同的祕密,外洩一個的影響範圍只有那一筆預約
- 改期 → 重新提醒時換新 token,上一封提醒信的連結失效(只存一個提醒 token)。接受這個取捨:確認信的連結仍有效,顧客不會被鎖在外面;若要連舊提醒連結也保留需要獨立的 token 表
- `worker::tick` / `run` 多一個 `public_base_url` 參數(信中連結的網址前綴);沒有隱含的預設值,免得正式環境不小心用了測試網址
- 對已確認的預約用提醒連結再按「確認」是無害的成功(冪等),不需要特別排除

## 2026-10-05 員工停用(離職)
- 動機:`bookings` 以外鍵參照員工,有預約紀錄的人刪不掉(之前只回 409)。刪除還會讓歷史預約失去員工名稱,所以改成**停用**(`memberships.active`),不是軟刪除整個使用者:同一個帳號可能還屬於別的店

- **有「未來已確認」預約就不准停用**(409 並說明筆數):顧客會撲空。解法是先取消 —— 顧客會收到剛做好的取消通知信。待確認的不擋(不佔時段,顧客來確認時會因員工已停用而自動失敗;`tests/worker.rs` 驗證);過去的不擋

- 自己「退出團隊」改走停用而非刪除:離職的人通常有歷史,刪除會失敗;停用不論有無歷史都成功。刪除(「移除」)保留給管理者,失敗時提示改用停用
- 已知缺口:沒有改派;檢查與新預約之間的極小競態(可能有 1 筆預約落在剛停用的員工,管理者看得到、可取消)—— 若要消除需要在建立預約時鎖住員工的成員資格列

## 2026-10-05 HttpOnly cookie 登入
- 動機:JWT 放 localStorage 時,任何一個 XSS 都能把 token 偷走帶著離開。改成 `HttpOnly` cookie 後,注入的腳本讀不到它(仍能在頁面開著時「借用」登入發請求,這是 cookie 方案本來就擋不住的,要靠 CSP 與不引入 XSS)
- cookie:`HttpOnly; SameSite=Strict; Path=/; Max-Age=JWT_TTL`,正式環境加 `Secure` 並用 `__Host-session`(瀏覽器保證不被子網域覆寫、不可帶 Domain)。開發環境是 http,所以名稱 `session` 且無 Secure
- **CSRF 不只靠 SameSite**:Strict 的「同站」以可註冊網域為單位,同網域下別的子網域(例如使用者內容的子網域)不會被擋。所以 cookie 認證的寫入請求另外檢查 `Origin` 白名單(精確比對,不用前綴),沒有 Origin 也拒絕。Bearer 不是瀏覽器自動帶的,不檢查
- Bearer 保留(測試與腳本),且**優先於 cookie**:帶了無效 Bearer 就是 401,不會退回去用 cookie,避免行為模糊。回應 body 仍附 token(非瀏覽器客戶端要用),網頁刻意忽略,型別也不宣告它
- 登出必須由伺服器做(JS 刪不掉 HttpOnly cookie):`POST /auth/logout` 不需登入、不檢查 Origin(最糟只是被強制登出)。後端連不上時前端仍登出(盡力而為,cookie 最久一小時過期)。JWT 本身仍無法撤銷;改密碼 / 重設密碼會讓所有舊 token(含 cookie)失效
- 前端不再存 token,啟動時 `GET /auth/me` 確認登入(`loading → in | out`,守衛等它,不然重新整理會閃登入頁)。跨分頁同步改用一個無機密的 `tenant-saas.auth-event` 訊號,收到就重新問後端。升級時主動刪掉舊的 localStorage token。啟動確認用 epoch 防止遲到的「未登入」蓋掉剛登入的人
- 代價:API 必須與網頁同源(原本就是);必須 HTTPS(`__Host-`/`Secure`);Origin 白名單要和實際網頁來源一致

## 2026-10-05 migration 0010 的建角色競態(CI 抓到)
- 症狀:CI 偶爾在 `failed to apply migrations: duplicate key ... pg_authid_rolname_index (tenant_runtime)`。sqlx 的每個測試各建一個資料庫並平行跑 migration,而**角色是整個叢集共用**:「先檢查有沒有、沒有才建立」在檢查與建立之間會被別的測試搶先
- 原本以為有防護:0010 開頭的 `pg_advisory_xact_lock` —— 但 advisory lock **只在同一個資料庫內有效**,各測試的資料庫不同,所以擋不住。0002 / 0007 本來就用「直接建立、吞掉重複錯誤」,只有 0010 漏了
- 修正:0010 改為同樣寫法。重現實驗(24 個連線同時、5 輪):舊寫法失敗 1 次,新寫法 0 次
- 代價:改了已套用的 migration,sqlx 校驗碼會對不上。專案尚未上線所以接受;本機開發資料庫要更新 `_sqlx_migrations` 的 checksum(SHA-384)。**一旦有正式環境,migration 就不能再這樣改**,要改請新增 migration

## 2026-10-05 拖曳改期
- 放開後**先確認再送出**:手滑成本高(會寄信給顧客),而且確認視窗是顯示後端拒絕原因(沒空、營業時間外、額度)的地方。前端不預先判斷能不能放,避免與後端規則不一致
- 用 HTML5 拖放而非自製指標事件:程式少、可測;代價是觸控不支援。拖曳只是捷徑,完整功能仍在「改期」視窗(鍵盤 / 觸控 / 螢幕閱讀器可用)
- 區塊外包一層 `div` 負責位置與拖曳,按鈕留在裡面:Firefox 不能直接拖 `<button>`;位置仍用 class(CSP 禁行內 style)
- 放開位置 = 區塊**上緣**對齊格線(扣掉抓取點),所以抓在區塊中段也不會偏移;夾在視窗第一格 ~ 最後一格;放回原位不動作
- 只有「已確認且還沒開始」的預約可拖,與詳情裡「改期」按鈕條件相同

## 2026-10-05 付款失敗通知信
- 觸發用 `invoice.payment_failed`(每次嘗試一個事件),不用訂閱狀態變成 `past_due`(只會發生一次,而且看不到金額與下次重試時間)。每次嘗試都寄:使用者在扣款前還有機會處理

## 2026-10-05 帳號鎖定
- 以**帳號**計數(不是 Email 字串):只對已存在的帳號寫入,不會被灌出無限多筆;不存在的 Email 永遠 401,所以鎖定不構成帳號列舉的管道。鎖定中對外仍是同一個 401,而且仍做一次雜湊運算,耗時相近
- 鎖定期間的失敗不計數、不延長:否則攻擊者可以讓受害者永遠登不進去。資料庫函式自己也擋,因為「檢查是否鎖定」與「記一次失敗」之間有空隙(同時進來的請求)
- 已知取捨:攻擊者可故意輸錯把他人鎖 15 分鐘。緩解:忘記密碼不受鎖定影響、重設密碼立刻解鎖、鎖定時寄通知信。依 IP 的限流(每分鐘)仍在,兩者互補
- 不寫 `audit_logs`:該表屬於店家(`tenant_id NOT NULL`),帳號層級事件沒有歸屬;改用日誌(只記使用者 ID)、指標與通知信
