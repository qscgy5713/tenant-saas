# 設計決策紀錄

格式:日期、決策、原因、替代方案。

## 2026-10-02 租戶隔離方式:共用表 + tenant_id + RLS
- **原因**:成本低、Rust 生態支援順、RLS 在資料庫層強制過濾,即使應用層漏寫條件也不會外洩
- **替代方案**:每租戶一個 schema(migration 複雜)、每租戶一個資料庫(營運成本高)
- **狀態**:暫定,M3 實作後驗證

## 2026-10-02 Web 框架:axum
- **原因**:tokio 生態主流,與 tower middleware 整合佳
- **替代方案**:actix-web

## 2026-10-02 資料庫存取:sqlx
- **原因**:編譯期檢查 SQL,不需 ORM 的額外抽象
- **替代方案**:sea-orm、diesel

## 2026-10-02 領域:預約排程(取代原暫定的充電場域管理)
- **原因**:使用者希望做大部分人都用得到的產品;預約排程顧客端人人可用,又有時段衝突、時區等真實技術挑戰
- **替代方案**:團隊任務管理(多租戶練習較完整但使用者偏上班族)、表單收集(太簡單)
- **取捨**:顧客不需帳號,成員關係較單純,以「員工可屬於多間店」補足

## 2026-10-02 RLS 套用方式:交易內 SET LOCAL ROLE tenant_app
- **原因**:單一連線池即可;擁有者 / 超級使用者預設繞過 RLS,切換成 `NOBYPASSRLS` 角色後才真正受約束;交易結束角色與上下文自動還原,不會殘留到下一個請求(有測試)
- **替代方案**:另開以 `tenant_app` 登入的第二個連線池(需管理兩組連線與密碼)
- **風險**:有人繞過 `begin_scoped` 直接對 `PgPool` 查租戶表,在超級使用者連線下會繞過 RLS。規則:租戶資料一律經 `begin_scoped`;正式環境連線使用者不可是超級使用者

## 2026-10-02 租戶不放進 JWT
- **原因**:使用者可屬於多間店,切換店家不必重新登入;每個請求用 `/t/{slug}/...` 即時驗證成員資格,停權或移除成員立即生效
- **取捨**:每個租戶請求多一次查詢(成員資格)

## 2026-10-02 非成員與店家不存在一律回 404
- **原因**:不洩漏某個網址代稱是否已被註冊 / 存在(有測試比對兩者回應完全相同)
