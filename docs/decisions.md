# 設計決策紀錄

格式:日期、決策、原因、替代方案。

## 2026-10-02 租戶隔離方式:共用表 + tenant_id + RLS
- **原因**:成本低、Rust 生態支援順、RLS 在資料庫層強制過濾,即使應用層漏寫條件也不會外洩
- **替代方案**:每租戶一個 schema(migration 複雜)、每租戶一個資料庫(營運成本高)
- **狀態**:暫定,M3 實作後驗證

## 2026-10-02 Web 框架:axum
- **原因**:tokio 生態主流,與 tower middleware 整合佳
- **替代方案**:actix-web

## 2026-10-02 資料庫存取:sqlx
- **原因**:編譯期檢查 SQL,不需 ORM 的額外抽象
- **替代方案**:sea-orm、diesel

## 2026-10-02 領域:預約排程(取代原暫定的充電場域管理)
- **原因**:使用者希望做大部分人都用得到的產品;預約排程顧客端人人可用,又有時段衝突、時區等真實技術挑戰
- **替代方案**:團隊任務管理(多租戶練習較完整但使用者偏上班族)、表單收集(太簡單)
- **取捨**:顧客不需帳號,成員關係較單純,以「員工可屬於多間店」補足

## 2026-10-02 RLS 套用方式:交易內 SET LOCAL ROLE tenant_app
- **原因**:單一連線池即可;擁有者 / 超級使用者預設繞過 RLS,切換成 `NOBYPASSRLS` 角色後才真正受約束;交易結束角色與上下文自動還原,不會殘留到下一個請求(有測試)
- **替代方案**:另開以 `tenant_app` 登入的第二個連線池(需管理兩組連線與密碼)
- **風險**:有人繞過 `begin_scoped` 直接對 `PgPool` 查租戶表,在超級使用者連線下會繞過 RLS。規則:租戶資料一律經 `begin_scoped`;正式環境連線使用者不可是超級使用者

## 2026-10-02 租戶不放進 JWT
- **原因**:使用者可屬於多間店,切換店家不必重新登入;每個請求用 `/t/{slug}/...` 即時驗證成員資格,停權或移除成員立即生效
- **取捨**:每個租戶請求多一次查詢(成員資格)

## 2026-10-02 非成員與店家不存在一律回 404
- **原因**:不洩漏某個網址代稱是否已被註冊 / 存在(有測試比對兩者回應完全相同)

## 2026-10-02 防重複預約:應用層驗證 + 資料庫排除約束
- **原因**:應用層「先查再寫」在併發下一定有空窗(有破壞性測試證明:拿掉約束後 8 個併發請求有 2 個同時成功)。約束是最後防線,應用層只負責擋明顯無效的請求並給友善錯誤
- **做法**:`EXCLUDE USING gist (tenant_id, staff_user_id, tstzrange(starts_at, ends_at)) WHERE status IN (confirmed, completed, no_show)`;違規(23P01)回 409,不指定員工時用 savepoint 退回再試下一位

## 2026-10-02 營業時間以本地時間儲存,計算時依時區換算
- **原因**:「每週一 09:00 開門」是本地概念,不隨夏令時間改變。若存 UTC,夏令時間切換後整套時間會偏一小時
- **夏令時間**:跳時造成的不存在時刻整段略過;回撥造成的重複時刻取較早者(皆有單元測試)

## 2026-10-02 公開預約防濫用
- 每來源限流(記憶體內固定視窗,預設 60 次 / 分鐘);單一 Email 最多 5 筆未來預約;最遠 90 天;既有顧客的姓名電話不被後續預約覆寫
- X-Forwarded-For 預設不信任,開啟後只取最右一筆(最右是自家代理附加的,左邊可被偽造)
- **已知缺口**:Email 未驗證。限流與上限只能提高成本,擋不住有心人用大量不同 Email 佔位,M6 寄確認信後改成確認才占位
- 多實例部署時限流各自計算,需要全域限流時改用 Redis

## 2026-10-02 顧客預約「確認後才占位」
- **原因**:先占位再驗證,攻擊者可用任意 Email 在限流下持續佔住時段;確認後才占位,沒有信箱控制權就占不到任何位置。壞處是兩人申請同一時段時,先按確認的贏,後者會在確認時收到衝突訊息(有測試)
- **做法**:`pending` 不在排除約束的條件內;確認那一刻轉 `confirmed`,衝突(23P01)就把這筆標為 cancelled。確認時還會重新驗證時段(申請後可能新增休假)
- **token 不回傳**:建立預約的回應不含管理 token,只在信裡;否則呼叫者可替別人的 Email 確認
- **確認用 POST**:信中連結導向前端頁面,頁面按下按鈕才送 POST。若用 GET,信件安全掃描器自動點開連結就會替對方確認
- **已知限制**:可對他人 Email 觸發驗證信(每店每 Email 最多 5 筆待確認 + IP 限流,24 小時後才釋出名額)

## 2026-10-02 寄信:資料庫 outbox + 內建 worker,不引入 Redis / 外部佇列
- **原因**:信與業務資料同一個交易寫入,不會「預約成功但信沒排進去」或相反;`FOR UPDATE SKIP LOCKED` 讓多個 worker 實例不會重複寄;少一個要維運的元件
- **取捨**:吞吐量上限比專用佇列低,對預約系統的信量遠遠足夠;日後量大再換
- **隱私**:信裡有一次性連結,寄出(或最終失敗)後立即清空 body,資料庫不長期保留 token;排程時間一律用資料庫時鐘

## 2026-10-02 背景 worker 的權限:獨立角色 `tenant_worker`
- **原因**:worker 要跨租戶處理,但不該是超級使用者。它沒有 BYPASSRLS,只對需要的表有明確政策與權限(測試證明:讀不到 `password_hash`、不能刪預約、不能寫服務、讀不到 memberships)

## 2026-10-02 限額的併發控制:per-tenant advisory lock,不用 SERIALIZABLE 或計數欄位
- **原因**:「先 count 再 insert」在讀已提交下一定會超賣。`pg_advisory_xact_lock(hash('quota:{種類}:{租戶}'))` 讓同一家店同一種資源的檢查+寫入序列化,不同店、不同資源互不阻塞,交易結束自動釋放
- **替代方案**:SERIALIZABLE(需處理重試,影響整個交易);獨立計數欄位(要和真實資料保持一致,刪除 / 取消時容易漏);
- **風險**:Rust 的 `plan::lock` 與 SQL 的 `accept_invitation()` 各寫一份鎖 key,改了一邊另一邊就失效。已有測試持有同一把鎖來驗證兩邊都會等待
- **取捨**:鎖範圍是整家店的某種資源,寫入量很大的店家會在該資源上排隊;預約系統的量級可接受

## 2026-10-02 限額語意
- 成員數 = 成員 + 未過期未接受的邀請(邀請會預留名額);撤銷或過期釋出
- 服務數 = 啟用中的服務(停用不算;重新啟用要重新檢查)
- 每月預約 = 該店當地月份內 confirmed / completed / no_show;取消不算,待確認不算。確認、員工代客預約、跨月改期都計入
- 降級後超出新上限的既有資料不強制清理,只擋新增
- 對顧客一律說「額滿」,不暴露方案名稱與上限;員工與 owner 才看到 402 與方案資訊

## 2026-10-02 方案只能由營運端改
- `tenant_app` 對 `plans`、`tenants.plan_id` 無寫入權限(測試證明),避免店家自行升級。升降級由之後的 Stripe webhook 或營運人員處理,尚未實作
